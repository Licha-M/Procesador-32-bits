# NOTAS DE DISEÑO: CONTROLADOR DE EXCEPCIONES Y DOUBLE FAULT

Este documento resume las decisiones de diseño y el funcionamiento propuesto para el Controlador de Excepciones y la detección de Double Fault en el hardware del procesador RISC de 32 bits.

---

## 1. Responsabilidades del Controlador de Excepciones (Hardware)

El controlador centralizado en hardware actúa como puente directo entre el Datapath (pipeline) y el software del Kernel:
1. Detección y Priorización: Recibe las señales de fallo de cada etapa del pipeline y prioriza la de la instrucción más antigua (la que está más avanzada en el pipeline):
   MEM (Page Fault) > ID (Invalid Opcode) > IF (Page Fault de Fetch)
2. Inyección de SCL: Reemplaza la instrucción fallida/siguiente por un SCL (Syscall) en el pipeline de manera controlada.
3. Guardado de Contexto: Genera las señales necesarias para escribir la dirección de retorno en el registro R1 (EPC) y el código del error en R7 (Cause).
4. Cambio de Modo: Modifica el estado del procesador para pasar a Modo Kernel (Privilegiado) y hace un Flush del pipeline para limpiar las instrucciones de usuario restantes.

---

## 2. Lógica y Detección de Double Fault (Fallo Doble)

Para evitar bucles infinitos causados por excepciones en cadena (por ejemplo, si el manejador de excepciones del Kernel sufre un Page Fault antes de estar listo):
* Flip-Flop de Estado (Handler_Active):
  * Se pone en 1 (Set) en cuanto el hardware procesa una excepción crítica (Page Fault, GPF, Invalid Opcode).
  * Se pone en 0 (Reset) únicamente cuando el procesador ejecuta la instrucción SRT (Syscall Return), lo que indica el fin seguro del manejador por software.
* Activación del Double Fault:
  * Si llega una nueva señal de excepción desde el pipeline y el Flip-Flop Handler_Active ya está en 1, el hardware ignora la causa original, configura Cause = 3 (Double Fault) y transfiere el control para detener la máquina (Kernel Panic).
  * Las excepciones ocurridas durante llamadas normales al sistema (SCL voluntario del usuario) no activan el flag Handler_Active en hardware, lo que permite que los Syscalls tengan excepciones anidadas (como Page Faults para paginación bajo demanda).

---

## 3. Estrategias para Evitar la Pérdida del EPC (Nesting)

Si ocurre una excepción durante un Syscall (por ejemplo, un Page Fault en el Kernel), el valor de R1 (EPC) de usuario podría sobrescribirse. Proponemos dos enfoques de solución:

### Enfoque A: Gestión por Software (Recomendado)
El hardware mantiene un único registro físico R1 (EPC).
* Flujo: Nada más entrar a SyS-JMP, el Kernel utiliza los registros shadow R14 y R15 para salvaguardar de forma inmediata el EPC de usuario y volcarlo en la pila física del Kernel en RAM.
* Ventaja: No requiere duplicar registros físicos en el bloque Registros.circ, manteniendo el hardware simple y elegante.
* Detalle: Está alineado con el principio crítico detallado en MEMORY_AND_ABI.md (line 32).

### Enfoque B: Duplicación por Hardware
El bloque de registros físico expone dos registros internos: EPC_User y EPC_Kernel.
* Flujo: El hardware conmuta automáticamente la escritura y lectura del EPC basándose en el bit de estado Modo_Kernel.
* Desventaja: Aumenta la complejidad de multiplexación en el banco de registros en Logisim.
